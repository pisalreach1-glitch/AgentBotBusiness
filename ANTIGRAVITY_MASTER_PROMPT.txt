1. PRODUCT GOAL AND SCOPE

Build ONE Telegram bot with THREE connected specialist workflows:
  📝 បង្កើតផែនការ — Project Planner
  🔎 ពិនិត្យផែនការ — QA & Reality Checker
  📣 រៀបចំការផ្សព្វផ្សាយ — Marketing & Community

These are three roles inside the same Telegram bot. Do not require three bot
tokens, three separate chat windows, or manual copying between specialists.
The primary user speaks Khmer and runs a small business, including cooking
courses. Support other small businesses without hard-coding one school name.
The owner wants clear buttons and one question at a time, not slash commands
as the main interface. Text fields remain necessary for goals and business data.

Target: a Windows PC using Python 3.11+, with a simple setup/start experience.
Use local SQLite persistence and Telegram long polling. The PC must be running
and online while the bot is available. Do not add hosting subscriptions.

IMPORTANT PROVIDER REQUIREMENT:
I use GOOGLE AI STUDIO. Use the Gemini Developer API and the official
google-genai Python SDK. Required environment keys are TELEGRAM_TOKEN and
GEMINI_API_KEY; GEMINI_MODEL must be configurable. Do not use Anthropic/Claude,
OpenAI, Vertex AI service accounts, an unrelated proxy, or a paid fallback.
Use the async SDK from async Telegram handlers; do not block them with sync

4. BUSINESS PROFILES AND PERSISTENT MEMORY

Support separate business profiles per Telegram owner. A profile includes:
  name, product/service/offer and known prices or conditions,
  target audience, budget with currency and period,
  main goal, available staff/time/capacity/channels.

Ask one short Khmer question per step. Offer Skip only for optional fields.
For editing a profile, provide Keep existing value. Let the user select an
existing business. Persist selected business, wizard flow, step and collected
answers in SQLite so /start can resume after a restart.

Separate private data by owner and business IDs. Every SELECT, UPDATE, export,
callback, task action and source-document lookup must validate ownership on

Keep generated artifacts immutable: changes create a new artifact linked to
the prior version. Save the profile/brief snapshot used to generate each plan.
Downstream QA/revision/marketing must receive the explicitly selected plan and
its snapshot rather than whatever global history happens to be most recent.

6. QA WORKFLOW

Allow either selecting a saved plan or submitting an existing plan as pasted
text or a UTF-8 .txt/.md file. Bound file size to 100 KB and text to 60,000
characters. Reject unsupported formats clearly instead of pretending to read
PDF, images or Word files. Those formats are outside this implementation.
Save an imported plan as an owner-scoped source artifact so it can be reviewed
and revised through exactly the same handoff workflow as a generated plan.

Review the actual plan for:
  clear goals and measurable outcomes;
  customer/offer fit and unsupported assumptions;
  practical timelines, capacity and dependencies;
  budget consistency and missing inputs;
  significant risks, missing work and unrealistic claims.

Output issues ordered HIGH / MEDIUM / LOW. Each issue must identify the actual
problem, why it matters, what evidence exists or is missing, and how to fix it.
Do not invent a success percentage or arbitrary score. Recognize strengths
only when the source demonstrates them. Do not silently overwrite the plan.

Provide ✏️ កែផែនការតាមយោបល់. This invokes the PLANNER with the original plan,
original profile/brief snapshot, and this specific QA result, saving a NEW
plan version. Preserve both the original plan and QA document.

8. CROSS-AGENT HANDOFF AND VERSION CONTRACT

Planner output -> QA button passes its artifact ID -> QA result -> revision
button passes BOTH the plan ID and review ID -> revised plan -> Marketing
button passes the revised plan ID. Never rely on an active global agent's
temporary history to carry these documents.

Store artifacts with at least:
  id, owner, business_id, kind (plan/review/marketing), parent_id,
  content, tasks JSON, request/profile/brief snapshot JSON,
  status (complete/incomplete), stop_reason, delivery state, created timestamp.

For a revision, parent_id links to the prior plan; include the used QA review
ID in the request snapshot. Provide a button to reopen the parent plan.
Paginate saved documents and validate owner on every page/action.

9. TASKS

A generated plan returns structured tasks. Accept them only after validating
the model output. A user explicitly activates a plan's task list. Repeated
activation must not create duplicate tasks. Activating another plan for the
same business changes the active checklist without deleting previous tasks,
completed status, source documents or another business's checklist.
Show the first three due/overdue/undated pending tasks under today's tasks;
allow viewing all active tasks. Provide Mark done buttons. Keep completion
state across restarts and do not reset it when the same plan is reactivated.
Use Asia/Phnom_Penh for the displayed local day; store timestamps in UTC.
Task dates must be ISO YYYY-MM-DD or null when unknown.

10. GEMINI ADAPTER AND OUTPUT VALIDATION

Use google.genai.Client with the explicitly configured API key and Gemini
Developer API, then await client.aio.models.generate_content(...).
Supply the specialist system_instruction, explicit business/source JSON,
response_mime_type='application/json', a JSON schema, and max_output_tokens.
Set a bounded timeout. Configure one SDK attempt: no hidden repeat generation,
paid fallback, silent model switching, automatic output-repair call, or quota
upgrade. Close async and sync client resources on shutdown.

Required model result shape:
  {
    "content": "complete Khmer answer",
    "tasks": [
      {"title": "concrete action", "due_date": null}
    ]
  }

The due_date is either a valid ISO date string such as '2026-11-01' or JSON null
when no deadline is known.
QA and Marketing return tasks: []. Plans should return 3-10 useful tasks, with
an absolute cap of 12. Validate JSON type, nonempty content, task length, dates
and bounds in application code even when schema-constrained output is enabled.

Inspect candidate.finish_reason. Normalize STOP to complete, MAX_TOKENS to an
incomplete draft, and safety/no-candidate/other failures to safe explicit error
handling. Do not reveal model thought parts. Never accept partial JSON as a
validated task list. Store useful incomplete text with a clear label, and do
not enable QA/Marketing/task-activation handoffs from that incomplete draft.

Use usage_metadata when available. Record prompt token count and generated
output including thought tokens separately from the request counter. These
are observed usage counters, not a money estimate or a guarantee of billing.
Handle 429 quota/rate limits with a short Khmer message referring to AI Studio.
Handle invalid keys/permissions and unavailable model IDs without revealing
raw exceptions or key values. Never automatically upgrade billing.

11. RELIABILITY, PRIVACY AND CONCURRENCY

Use private chats only. Reject group access BEFORE loading private business
data. If an allowlist is configured, enforce it before state/document access.
Add per-owner async locks; keep different owners separate. For parallel update
processing, do not use an unsafe shared ConversationHandler state. Ensure old
Skip/Keep callbacks contain wizard ID + step, so a stale double click cannot
answer the next question or corrupt a later wizard.

Persist API request reservations and outcomes. The same Telegram event must
not cause two outbound model calls. Repeated successful QA and QA-driven
revision buttons should reuse the saved result; an explicit Regenerate action
is a new request. A failed request can be retried on a new explicit click.
Enforce a per-owner daily request cap before sending the outbound call. Count
failed started requests too. This cap is not a Google provider quota limit.

Persist a successful generation before Telegram delivery. Track pending,
partial, failed and sent delivery states. Only mark sent after every chunk was
sent. Let the user reopen/resend a saved result without another model call.
A failed typing indicator must not prevent generation.

Send plain text with conservative UTF-16 chunk sizing below Telegram's limit;
preserve all Khmer text, whitespace and emoji. Keep callback_data within 64
UTF-8 bytes. Acknowledge callback queries promptly.

Use WAL, foreign keys, bounded transactions and a schema version for SQLite.
Use a single-process lock before startup recovery, so a second process cannot
mistake an active request for a crash. Interrupted requests must not be replayed
silently after restart. Provide clear recovery through a new user action.

Keep credentials in .env, ignored by git. Do not log user text, bot-token URLs,
raw provider errors, API keys or environment contents. Give safe Khmer user
messages and log only safe error types/reference information.
